# Spec: kinds of entities (`extends`), and warnings for things said twice

Written 2026-11-27 for Vinay to decide on. **Status: built 2026-11-27**, every decision as recommended (Vinay approved all 30). What differs from the text below is in "What changed during the build" at the end.

Vinay asked whether Lorefile follows four common ontology design principles:
- domain-driven design
- don't repeat yourself, with the rule of three
- open for extension, closed for modification
- producer extends, consumer super

The answer was mostly yes, with two gaps:
1. **Nothing lets an entity be a kind of another.** You can't say "a promo sale is a kind of sale", so its fields are written again, and imported class hierarchies arrive as tags (`subclass-of:Intangible`).
2. **Nothing notices when the same thing is said twice.** Two metrics with the same recipe, two entities reading the same rows, or one word meaning two things all pass silently.

This spec closes both. Links between spaces stay for later (BACKLOG).

**Base:** branch `claude/learn-file-6a954e` at `8f8ba8e`, plus the two specs being built on it now:
- [2026-11-27-ui-fixes.md](2026-11-27-ui-fixes.md) (its words)
- [2026-11-27-home-plane.md](2026-11-27-home-plane.md) (its `/api/plane`, lights and layout)

"Touches" in each part says where this spec changes theirs.

**Standing rules, unchanged:**
- The ontology never executes and never holds credentials. Rows never enter the ontology.
- Agents and builders write the YAML; people review it.
- Light theme only.
- Honest status.
- The format refuses unknown keys (`deny_unknown_fields`), which catches typos. This spec keeps that.

**Read first:**

## Before and after

### One entity that is a kind of another

There are two ways rows can relate, and Lorefile supports both.

**Kind A: the rows are a slice of the parent's rows.** One `orders` table holds every sale, and a `kind` column says which are promos.

Before: write PromoSale out in full, or don't write it at all.

```yaml
# types/promo_sale.yaml  (before: a copy of Sale with a different name)
type: PromoSale
description: A sale made with a promo code.
properties:
  line_id:    { type: string, key: true, description: One order line. }
  order_id:   { type: string, description: The order it belongs to. }
  revenue:    { type: number, unit: USD, description: What the customer paid for the line. }
  # … 6 more fields, the same as Sale's, which drift apart the first time one is edited
  promo_code: { type: string, description: The code used. }
source: { connection: shop, table: orders, key: line_id }   # the same rows as Sale: nothing says only promos
```

After:

```yaml
# types/promo_sale.yaml
type: PromoSale
extends: Sale                       # a kind of Sale: every Sale field, link and guardrail applies
description: A sale made with a promo code.
where: { kind: promo }              # which of Sale's rows are PromoSales
properties:
  promo_code: { type: string, required: true, description: The code used. }   # only its own fields
```

**Kind B: the rows come from somewhere else.** This is branda's case. PromoSale is learned from a promo export (`user_files.promo_sales`), while Sale would come from the shop's own orders.

```yaml
type: PromoSale
extends: Sale
description: One order line from the monthly promo export.
properties:
  promo_code: { type: string }
  campaign:   { type: string }
source: { connection: user_files, table: promo_sales, key: line_id }   # its own rows
```

### What an agent reads

Before, `describe PromoSale` lists 14 fields and says nothing about Sale.

After:

> **PromoSale is a kind of Sale.** It has Sale's 9 fields (line_id, order_id, order_date, revenue, …) plus 2 of its own: promo_code, campaign. Sale's links (placed_by → Customer) and Sale's 3 guardrails apply to it too.
>
> **Rows:** its own, in user_files.promo_sales, a file a person gives you. They may also be among Sale's rows: never add a Sale number and a PromoSale number together. Ask the user if a total needs both.

For kind A, the rows line reads instead:

> **Rows:** Sale's rows where kind is promo (shop.orders). Every number about Sales already includes PromoSales.

### Something said twice

Before, a second metric with the same recipe passes silently:

```
metrics: [ { metric: promo_sale_revenue, source: { connection: user_files, table: promo_sales, filter: refunded = false, measure: sum(revenue) } },
           { metric: promo_revenue,      source: { connection: user_files, table: promo_sales, filter: "NOT refunded", measure: SUM(revenue) } } ]
```

After, on the review screen before Accept:

```
⚠ Promo revenue looks the same as Promo sale revenue: same rows, same filter, same sum.
  Agents would have two names for one number.
  ( ) Accept anyway: they are different on purpose. Why? [ promo_revenue will include tax from January ]
  [ Not now ]  ← usually the right answer: ask the agent to use promo_sale_revenue
```

## Decisions

All for Vinay. The recommendation is in bold.

| # | Question | Options | Recommendation |
|---|---|---|---|
| 1 | The key | **A. `extends: Sale` on a type.** B. `kind_of: Sale`. C. `parent: Sale` | **A.** It is the word Ossie uses, and readers of RDF and code know it. The page says "a kind of" (decision 30). |
| 2 | How many parents | **A. One.** B. Several | **A.** Several parents bring field clashes and diamond questions agents get wrong. An import with several keeps the first as `extends` and the rest as tags, as today. |
| 3 | How deep | **A. Up to 6 levels; a loop is an error.** B. No limit | **A.** Deep chains are hard for agents to follow and a sign of over-modelling. Six covers schema.org's deepest common chains (`Thing → Organization → LocalBusiness → Store`). |
| 4 | Fields | **A. Inherited. A kind may redeclare a parent's field only to narrow it: its own description, `required: true`, fewer enum values. Changing its type, unit or key is an error.** B. Free override. C. No redeclaring | **A.** Narrowing keeps "every PromoSale is a Sale" true. |
| 5 | The key | **A. Inherited and fixed: a kind can't name a different key. When the parent has none, a kind may have its own.** B. Free | **A.** A PromoSale and the Sale it is are one row, so they share an identity. |
| 6 | Links | **A. Inherited (PromoSale.placed_by works). A kind may add links but not reuse a parent's link name. A link that ends at Sale accepts any kind of Sale.** B. Not inherited | **A** |
| 7 | Guardrails | **A. Rules on Sale apply to every kind of Sale; a kind can add its own. Never the other way round.** B. Per entity only | **A**: "closed for modification". |
| 8 | Where a kind's rows are | **A. Two shapes. `where: {field: value}` picks the parent's rows (kind A). An own `source:` gives separate rows (kind B). Never both.** B. Own `source:` only. C. A free SQL filter | **A.** `where` covers the common one-table case and stays safe: structured, so no SQL is injected into a view, and it works for csv rows that never reach DuckDB. Anything subtler needs its own source. |
| 9 | `where`'s form | **A. A map of a parent's field to one value or a list of values. All must match.** B. A CEL or SQL expression | **A.** It turns into SQL with quoted identifiers and literals, into a Rust check for csv and inline rows, and into SHACL `sh:hasValue` / `sh:in`. It can also be compared for duplicates. |
| 10 | Does `instances(Sale)` include kinds | **A. It returns Sale's own rows. That already includes every `where` kind, and never separate-rows kinds.** B. Union the separate kinds in | **A.** A union is how double counting starts (branda's promo export lines are also shop orders). `describe` says which kinds are included. |
| 11 | Metrics over a parent | **A. They count what the parent's rows hold. `describe` of the metric says "includes PromoSales" (`where` kinds) or "does not include PromoSale's separate rows". Agents are told never to add a parent's number and a kind's.** B. A key on each kind saying whether its rows are also in the parent's | **A** now. B is left for later, once someone needs it. |
| 12 | Grades | **A. No grade is inherited. A `where` kind's source is graded on its own, and its fingerprint includes the parent's source, so a change to Sale's source makes PromoSale's "changed since" too. Rules on Sale keep one grade.** B. Accepting the parent grades the kinds | **A.** Each grade is one person's word about one thing. |
| 13 | Producer extends | **A. An action or function input that takes a Sale accepts any kind of Sale. `validate` works out the kind from the row (`where` kinds) or from a new `kinds` argument, and applies that kind's guardrails too.** B. Exact types only | **A** |
| 14 | Consumer super | **A. An input that takes a PromoSale refuses a plain Sale, in words ("S-1 is a Sale whose kind is wholesale, not a PromoSale"). W107 checks links and inputs the same way.** B. Warn only | **A** |
| 15 | Compatibility | **A. `format: 2` in ontology.yaml. Lorefile writes it in the same save whenever it writes `extends`, `where` or `distinct:`; a hand edit without it gets W118. From 0.2.0, a space whose format is newer than the binary gets a sentence saying to upgrade.** B. A release note only | **A.** Lorefile 0.1.0 shipped today and refuses `format:` (and `extends`) as an unknown field. That message points at the right file. Every version after it says plainly what to do. The same mechanism later carries `icon:`. |
| 16 | Duplicate warnings | **A. Three warnings: W115 for the same metric twice, W116 for the same entity twice, W117 for one word meaning two things. Warnings, never errors.** B. Errors | **A.** "Probably said twice" can be wrong; a person decides. |
| 17 | "Different on purpose" | **A. Kept in `trust.yaml` under `distinct:`, with who, when, why and both fingerprints. Committed, shared, written only by Lorefile. A meaningful change to either side brings the warning back.** B. `.lorefile/` (local). C. A key in the ontology files | **A.** It is a person's word about the ontology, which is what `trust.yaml` holds. `.lorefile/` is hidden from git, so a teammate would see the warning again. |
| 18 | The rule of three | **A. Advice, not a warning. When three or more entities share a core of fields, the review screen and `validate` offer "these could be kinds of one parent". Nothing turns amber.** B. A warning at two | **A.** Two similar entities are usually one entity (W116) or two flat ones. A parent is worth it at three. |
| 19 | Acting on the advice | **A. A `make_parent` op: one proposal that adds the parent with the shared fields and makes each entity extend it, dropping the fields now inherited. Plus a `set_kind_of` op for one entity.** B. Advice only; people edit YAML | **A.** Without the op, the advice is homework. |
| 20 | `match_file` and kinds | **A. A file with every field of an entity plus extra columns is offered as "a kind of Sale?" only when that entity already has a kind. Otherwise today's answer stands (Sale gets the new columns).** B. Always offer a kind | **A.** That is the rule of three again: a family exists once a person has made one. |
| 21 | `learn_file` | **A. A new optional `kind_of` in the answers. The draft extends that entity and holds only the extra columns; it is refused in words if the file lacks the parent's key.** B. Nothing | **A** |
| 22 | Agents told the rule | **A. One sentence in the server instructions: don't create a parent until three entities share fields; use `extends` when a person asks or `match_file` suggests it.** B. Nothing | **A** |
| 23 | RDF import | **A. `rdfs:subClassOf` between imported classes becomes `extends`, and parents come along by default (up to 6 levels, not `owl:Thing`), so fields on `Thing` reach `Person`. `--no-parents` keeps today's tags.** B. Only classes already selected | **A.** That is BACKLOG item 6's schema.org case. |
| 24 | RDF and SHACL export | **A. `rdfs:subClassOf` on the class. The kind's shape has `sh:node` to the parent's shape plus its own properties. `where` becomes `sh:hasValue` or `sh:in`. Lorefile's own `lf:where` keeps it exactly.** B. `rdfs:subClassOf` only | **A.** `sh:node` makes the parent's constraints apply whatever the data graph says. |
| 25 | Ossie | **A. A concept's `extends` is read (first entry; the rest kept as tags with a note) and written.** B. Keep dropping it | **A** |
| 26 | Inherited fields' IRIs | **A. Inherited fields keep the parent's IRI. Only own fields get `…/PromoSale.promo_code`.** B. One per entity | **A.** Otherwise an explicit `iri:` on a parent field would be "two things with one IRI" (E016) in every kind. |
| 27 | Where the compiler puts inherited fields | **A. Copied into the compiled kind (`properties`), each marked with where it came from (`inherited`). Writers and exporters use own fields.** B. Looked up from the parent on every read | **A.** About 30 places read `t.properties` (describe, data, rules, review, learn, plane), and they get it right with no change. Links are not copied: `outgoing`, `incoming`, `neighbors` and `path` follow the parent instead, because copies would show in exports and counts. |
| 28 | Deleting or renaming a parent with kinds | **A. Refused by the save gate, which already refuses new errors. The message names the kinds ("PromoSale and WholesaleSale are kinds of Sale"), and the review screen lists them under "still uses it".** B. Turn the kinds flat automatically | **A.** A person decides what happens to the kinds. |
| 29 | Shipped examples | **A. None changed in v1. Test fixtures carry the cases.** B. Add a kind to `ecommerce` | **A**, revisited after Vinay has used it. |
| 30 | Words on the page | **A. "a kind of Sale" and "Kinds of Sale: …". Never subclass, subtype or child.** B. "Sub-kind" | **A.** It adds one row to the UI-fixes words table. |

## Part 1 · The format

### The keys

| Key | Where | Says |
|---|---|---|
| `extends: Sale` | a type | this entity is a kind of Sale |
| `where: { kind: promo }` | a type with `extends` | its rows are Sale's rows that match; values can be lists: `{ channel: [email, sms] }` |
| `format: 2` | ontology.yaml | written by Lorefile when the space first uses either key, or `distinct:` in trust.yaml |
| `distinct:` | trust.yaml | pairs a person said are different on purpose (Part 6) |

`TypeDef` gains `extends: Option<String>` and `where_: Option<IndexMap<String, OneOrMany>>` (serde name `where`), both `skip_serializing_if = "Option::is_none"`. `TrustBook` gains `distinct: Vec<Distinct>`. `Manifest` gains `format: Option<u32>`. Everything stays `deny_unknown_fields`.

### Compatibility

| Binary | A space with `format: 2` and `extends` |
|---|---|
| 0.1.0 (shipped today) | Refuses to load with E001 for `ontology.yaml` ("unknown field `format`") and the type files ("unknown field `extends`"). Nothing to change there; the release note says what it means. |
| 0.2.0 (this) | Loads it. |
| 0.2.0 with a `format: 3` space | Refuses with one sentence: "This space needs a newer Lorefile (format 3); this is Lorefile 0.2.0, which reads format 2. Upgrade with `npx lorefile@latest` or `cargo install lorefile`." It is E019, and it takes the place of the unknown-field errors it would otherwise print. |

- **Who writes `format: 2`.** Any Lorefile save (the page, `propose_*`, `learn_file`, an import) that writes `extends`, `where` or `distinct:` writes `format: 2` into ontology.yaml as part of the same save, in the same commit. A hand-written `extends` without it compiles, with W118: "this space uses extends but ontology.yaml doesn't say format: 2; Lorefile 0.1.0 will not load it".
- **A space with no `format:`** is format 1, as every space today is.
- **The release note** (CHANGELOG and the GitHub release), in these words:

  > **Kinds of entities.** An entity can now be a kind of another (`extends: Sale`), with `where:` to pick the parent's rows. A space that uses them says `format: 2` in ontology.yaml, and Lorefile 0.1.0 refuses to load it ("unknown field `format`"). Upgrade every copy that reads the space first.

## Part 2 · What a kind gets from its parent

The compiler resolves kinds after loading, parents before kinds (topological order). Each compiled kind carries everything below.

| What | Rule | If broken |
|---|---|---|
| **Fields** | Every parent field, in the parent's order, then its own. Each copied field is listed in `TypeDef.inherited` (field → the entity it comes from), and that map is never written to files. | |
| redeclaring a parent field | Allowed to narrow: its own `description` (which wins for this kind), `required: true`, an enum's `values` as a subset, and `unit` only when the parent had none. | E021: "PromoSale.revenue is money (USD) in Sale; a kind can't make it a whole number" (for a type, unit or loosened `required` or wider enum) |
| **Key** | The parent's key. A kind may repeat `key: true` on the same field. | E022: "Sale is identified by line_id; PromoSale can't be identified by order_id". Only when the parent has a key. |
| **Links** | Not copied. `outgoing` / `incoming` / `neighbors` / `path` include the parent's links, marked "from Sale". A link ending at Sale accepts any kind of Sale. A kind may add links. | E023: "PromoSale.placed_by already comes from Sale" (a parent's link name reused) |
| **Guardrails** | `constraints_for(PromoSale)` includes rules on Sale (and on Sale's links), marked "from Sale". | |
| **Actions and functions** | `actions_involving(PromoSale)` includes those taking a Sale: "can be passed to refund_sale, which takes a Sale". | |
| **Glossary** | Words stay on what they name. A word meaning Sale is not a word for PromoSale. | W117 covers clashes (Part 6) |
| **Domain** | A kind without its own `domain:` (or manifest listing) is in its parent's. | |
| **Description** | Its own. Without one: W101 as for any entity. Sale's description is never borrowed. | |
| **Inline `instances:`** | A kind may have its own (reference data) only when it has no `where` and no `source`. | E024 |
| **`where`** | Only with `extends`; not with an own `source`; only parent fields; values must fit the field's type and, for an enum, be among its values. | E024: "where needs extends", "PromoSale has both where and a source: a kind picks its parent's rows or has its own, not both", "where names `knd`, which Sale has no field called" |
| **IRIs** | Inherited fields keep the parent's field IRI (`iri_field(PromoSale, revenue)` → Sale's). The kind's own IRI is derived from its name as usual. `resolve_iris` and the E016 / W112 checks walk own fields only. | |
| **Loops and depth** | `extends` must name an existing entity, form no loop, and be at most 6 levels deep. | E020: "PromoSale extends Sal, which doesn't exist", "Sale → Order → Sale goes round in a circle", "7 levels of kinds: at most 6" |
| **Several parents** | `extends: [A, B]` | E020: "an entity extends one other entity; `extends: [A, B]` names two" |

What else changes in the validator:
- **Per-field warnings use own fields only** (W101 field words, W105). A field without words is the parent's to fix. A kind's "fields without words" counts own fields only, here and in `/api/plane` (touches home-plane, Part 2's amber rule).
- **W104** allows a rule on PromoSale to read inherited fields and `sale.` as well as `promo_sale.`.
- **The DuckDB `nodes` table** gains an `extends` column, and `properties` an `inherited_from` column, so `query` can ask about kinds.

## Part 3 · Rows, numbers, and counting once

### A `where` kind (kind A)

| Where rows are read | How |
|---|---|
| DuckDB (parquet, duckdb, …) | `CREATE VIEW promo_sale AS SELECT * FROM sale WHERE "kind" = 'promo'`, with identifiers through `ident()` and values through `lit()`. A list becomes `IN (…)`. It is built after the parent's view and **before the fence is set**, like every view. No SQL from the YAML reaches DuckDB; the fence and `check_read_only` are unchanged. |
| csv (read in Rust) and inline rows | `data.instances(PromoSale)` reads Sale's rows and keeps those whose `kind` equals `promo` after the usual coercion (`coerce`). `find` looks the key up in Sale's rows, then checks `where`. |
| The parent isn't readable here (BigQuery, MCP, `from_user`) | `where_is(PromoSale)` says "Sale's rows (in shop_bigquery.orders) where kind is promo: fetch them with your own connector and keep those". |
| The parent has no rows at all | The kind has none either; `describe` says "no data yet", as for any unbound entity. |

Grading its source:
- **A `where` kind's source** is graded like any binding: `trust::things(Binding)` gets an entry for it. Its fingerprint covers its name, the key, `extends`, `where`, the parent's effective source and what that reads.
- **Re-pointing Sale's source** therefore makes PromoSale's source "changed since" too, and the reason says why: "because Sale's source changed".

### A kind with its own rows (kind B)

- **Its own `source:`** works exactly as an entity's does today: views, csv, `from_user`, `where_is`.
- **Columns:** its own `columns:` mapping covers inherited fields too, so a promo export whose key column is `line` maps `line_id: line`.
- **Not in the parent's rows:** `instances(Sale)` never includes these rows.

### Numbers

What each metric counts, as `describe` (of the metric) and `summary` say it:

| Metric reads | Says |
|---|---|
| Sale's rows, no `where` kind involved | "Counts Sales." |
| Sale's rows, Sale has `where` kinds | "Counts every Sale, PromoSales and WholesaleSales included." |
| Sale's rows, its filter includes all of PromoSale's `where` (`kind = 'promo'` among its AND-ed equalities) | "Counts PromoSales (Sale's rows where kind is promo)." Shown on PromoSale, not Sale. |
| a kind's own rows (kind B) | "Counts PromoSale's own rows (user_files.promo_sales). Sale's numbers don't include them; they may cover the same sales, so never add the two." |

- **The sentence agents get in `summary`**, once, when the space has any kinds: "A kind's numbers are part of, or beside, its parent's: never add a parent's number and a kind's number. Ask the user when a total seems to need both."
- **Touches home-plane:** the metric-to-entity match (Part 7 there) uses this table. A metric over Sale's table belongs to the deepest `where` kind whose equalities all appear in its filter, else to Sale.

## Part 4 · Producer extends, consumer super

### `validate` (the `check_action` behind it)

| The action takes | The agent passes | What happens |
|---|---|---|
| `sale: Sale` | a key found in Sale's rows | Resolved as today. When the row matches PromoSale's `where`, it is checked as a PromoSale: Sale's and PromoSale's guardrails both apply, and the answer says "checked as a PromoSale (a kind of Sale), because kind is promo". |
| `sale: Sale` | an inline record with `kind: promo` | The same: `where` is checked on the record. |
| `sale: Sale` | `kinds: { sale: PromoSale }` (new, optional) | Treated as a PromoSale. The key is looked up in PromoSale's rows (its own, for a kind B). Its guardrails apply. |
| `sale: Sale` | `kinds: { sale: Customer }` | An error: "Customer is not a kind of Sale". |
| `promo: PromoSale` | a key found in Sale's rows that doesn't match `where` | An error: "`promo` needs a PromoSale; S-1 is a Sale whose kind is wholesale". That is consumer super. |
| `promo: PromoSale` | a key, PromoSale is kind B and readable | Looked up in PromoSale's own rows, as today. |
| a link effect `placed_by` (from Sale) | a PromoSale for the `from` side | Fine: the link is inherited. |

- **Binding variables:** in `evaluate_all`, a rule on Sale binds to every input whose kind is Sale or a kind of Sale, with `sale`, the kind's own name (`promo_sale`) and `self` all set.
- **Two sibling kinds both match a row** (their `where`s overlap: W116): both kinds' guardrails apply, and the answer names both.
- **The `validate` tool's schema** gains `kinds`: "input name → the kind of entity this input is, when it is a kind of the type the action takes".

### Static checks

- **W107**, an action's link effect against its inputs, accepts an input whose type is the link's end or a kind of it.
- **An input broader than the link's end** ("`sale` is a Sale, but `promoted_by` starts at PromoSale") is now W107's message: "pass a PromoSale, or start the link at Sale".
- **E005**, for an action or function naming an unknown type, is unchanged.

### Functions

Lorefile never runs a function, but it tells agents what fits:
- `describe` of a function whose output is a PromoSale says "its PromoSale fits anything that takes a Sale: refund_sale".
- An input that takes a Sale says "any kind of Sale: PromoSale, WholesaleSale".

## Part 5 · What agents are told

- **`describe(PromoSale)`**:
  - JSON gains `extends`, `kinds` (its direct kinds), `where`, and `from` on each property, link and guardrail that comes from a parent.
  - The markdown opens with the "is a kind of" sentence and the rows line (Before and after).
- **`describe(Sale)`** adds "Kinds of Sale: PromoSale (where kind is promo), WholesaleSale (its own rows in wholesale.csv)".
- **`summary`** lists a kind under its parent, `PromoSale — a kind of Sale; 2 own fields; where kind is promo`, and adds the never-add sentence once when the space has kinds.
- **`where_is`** follows Part 3.
- **`search`** finds kinds by name as today. A hit on Sale lists its kinds.
- **Server instructions** gain one sentence in both the read and propose variants (`mcp.rs`, beside `FILE_RECIPE`):

  > Entities can be kinds of others (`extends`). Don't create a parent entity until three entities share the same fields; two similar entities are usually one entity, or two that stay separate. Use `extends` when the user asks for it or `match_file` suggests it.

- **`propose_patch` ops:**
  - `add_type` takes `extends` and `where`.
  - New `set_kind_of { type, extends, where? }`:
    - It makes an existing entity a kind of another.
    - It drops its fields that are now inherited unchanged (same type and unit, and a description that is equal or empty).
    - It keeps a differing description as a narrowing.
    - It refuses on any E021 or E022 conflict, naming the field.
  - New `make_parent` (Part 6).
  - All are planned by `patch::plan_in`, so the review screen compares them like any other.

## Part 6 · Things said twice, and the rule of three

### The warnings

| Code | Fires when | Says |
|---|---|---|
| **W115** | Two metrics have the same connection and table (or tool and params), the same `measure` and the same `filter` after normalising: case, whitespace, quotes, `=` vs `==`, `NOT x` vs `x = false`, and the order of AND-ed terms. Variants are compared one by one. | "Promo revenue looks the same as Promo sale revenue: same rows, same filter, same sum. Agents would have two names for one number." |
| **W116** | Two entities that are not parent and kind:<br>(a) are bound to the same connection and table (or tool and params) with the same or no `where`; or<br>(b) both have 4 or more own fields and 80% or more of the larger one's own field names match (normalised, as `learn::normalize_header`); or<br>(c) are sibling kinds whose `where`s can match the same row. | "PromoSale and PromoLine read the same rows (user_files.promo_sales): probably one entity." · "… share 12 of 14 fields: probably one entity." · "PromoSale and DiscountSale both pick Sale's rows where kind is promo." |
| **W117** | One glossary word means two different things, or a glossary word is another entity's own name. Today `type_()` silently picks the first. | "\"promo\" means both PromoSale and Promotion: agents will pick one at random." · "\"Order\" is an entity, and also a word for Sale." |

Rules:
- **None of them is an error.** All three are warnings, so the save gate lets them through and a person decides.
- **Lights:** they make the items amber on the home plane, with their sentence as the reason (touches home-plane: three new rows in Part 2's amber column).
- **The review screen** lists any W115, W116 or W117 that the proposal adds, as a question before Accept (touches review flow: `review::questions` gets three new entries):
  - `( ) Accept anyway: they are different on purpose. Why? [ … ]`. Choosing it sends a `distinct` fix with Accept.
  - Or Not now with a why, which `match_file` and the agent see. That is usually the right answer: the agent should reuse what exists.

### "Different on purpose" (`distinct:` in trust.yaml)

```yaml
trust:
  distinct:
    - { a: "metric:promo_revenue", b: "metric:promo_sale_revenue", by: "Vinay via page", at: "2026-11-27",
        of_a: "3c1e…", of_b: "d4fd…", why: "promo_revenue will include tax from January" }
```

How it behaves:
- **Written only by Lorefile**, from the review screen's "different on purpose" or a "These are different" button beside the warning on the entity or Logic page. It needs a name and edit mode, like every decision (UI-fixes Part 4).
- **The warning stays quiet** while both fingerprints match (`trust::things` for metrics; for entities, their name, own fields, source and `where`). When either side changes in meaning, the warning returns with "changed since Vinay said these were different (27 Nov)".
- **A side deleted:** its `distinct` line is an orphan and goes on the next save, like a W114 grade.
- **Never written by an agent:** an agent's `propose_*` can't add `distinct:`, as it can't grade.

### The rule of three, as advice

`validate::advise(ont) -> Vec<Advice>` is separate from diagnostics, so it never touches lights, counts or exit codes.

- **When it fires:** three or more entities (not already kinds of one parent) share a core of at least 4 fields with the same names and the same types, and the core is at least half of each one's own fields.
- **What it says:** "PromoSale, WholesaleSale and ReturnLine share 8 fields (line_id, order_id, order_date, sku, units, unit_price, discount, revenue). They could be kinds of one parent." It offers [Make a common parent…].
- **Where it shows:**
  - the review screen, under a proposal that creates the third (an "A suggestion, not a problem" box)
  - the Entities page of each of them
  - `validate`'s output under `advice`
- **What it never does:** fire for two entities (that's W116 at 80%, or nothing), or turn anything amber.

### `make_parent`

`{ op: "make_parent", name: "Sale", description?, children: [PromoSale, WholesaleSale, ReturnLine], fields?: [..] }` produces one batch:

1. A new `types/sale.yaml` with the shared fields:
   - by default, the advice's core
   - each with the most common description among the children (ties go to the first child), the shared type and unit
   - the key, if every child has the same key field
2. Each child gets `extends: Sale`, and loses the fields that are now inherited unchanged. Differing descriptions stay as narrowings. Its own source stays (each child is a kind B).
3. `format: 2` in ontology.yaml.

It refuses, in words, when:
- a shared field has different types or units in two children
- the name is taken
- a child already extends something else

The review screen shows it as "+ Sale, a new entity · PromoSale, WholesaleSale and ReturnLine become kinds of Sale". Each child's dropped fields are listed as "now from Sale", not as removals.

## Part 7 · `learn_file` and `match_file`

| The file | `match_file` answers |
|---|---|
| exactly an entity's columns | `same`, as today (kind B kinds match on their own columns: inherited plus own, through their `columns:` mapping) |
| an entity's columns plus extras, and that entity **has a kind already** | `changed`, with a new `kind_of` option. The `say` reads "This looks like a kind of Sale: Sale's 9 columns plus promo_code and campaign. Ask: is this a kind of Sale, or should Sale get these columns?" |
| an entity's columns plus extras, and the entity has no kinds | `changed`, as today (the new columns are offered to that entity) |
| a file whose columns match a `where` kind's parent | the parent answers. `where` kinds are slices of the parent's rows, never files of their own, so `match_shape` skips them. |
| a new file that would be the third sharing a core with two entities | `new`, plus `advice`: "with PromoSale and WholesaleSale this shares 8 columns: a common parent could hold them. Mention it, don't act on it." |

- **`learn_file` answers gain `kind_of: "Sale"`.**
  - The draft gets `extends: Sale`, its own source (the file) and only the columns Sale doesn't have, as fields.
  - Sale's key column must be in the file, mapped by name or `columns:`. Otherwise it is refused in words: "promo_sales.csv has no line_id, so its rows can't be Sales; learn it as its own entity".
  - Column types that conflict with Sale's (E021) are refused the same way, naming the column.
- **Questions** follow the learn-file spec. When the parent already has a metric, the "which number?" question offers "the same as Sale: Sale revenue" first.
- **A learned kind's metric** is named `<kind>_<column>` as today. It is a separate metric over the kind's own rows, and W115 can't fire against Sale's, because the rows differ.

## What this does not do

- **No several parents, no interfaces or mixins.**
- **No union of separate kinds' rows** into the parent's `instances` or `query`.
- **No free SQL in `where`.**
- **No key saying whether a kind B's rows are also in the parent's**: decision 11, and Left for later.
- **No links between spaces.**
- **No automatic flattening or merging.** W116 says "probably one entity". Merging is a person's `propose_change` or a later op.
- **No change to how grades work**, apart from `distinct:` and the `where` kind's binding fingerprint.
- **No change to the shipped examples.**

## Edge cases

| Case | What happens |
|---|---|
| `extends: Sale` where Sale is in a shipped example, not this space | E020: there is no Sale here. Links between spaces are for later. |
| `extends: sale` (wrong case) | Resolved case-insensitively, like every name (`type_`). The compiled kind and `describe` use the entity's real name, Sale. The file is left as written. |
| `extends:` naming a glossary word | Not followed: `extends` must name an entity, not a word. E020 says "`Order` is a word for Sale; extend Sale". |
| A kind of a kind (`ClearanceSale extends PromoSale extends Sale`) | Fields come down both levels. `where`s combine (a ClearanceSale is Sale's rows where kind is promo **and** clearance is true). Guardrails from both parents apply. |
| A `where` kind of a kind B parent | Its rows are the kind B parent's own rows that match. |
| A kind B kind of a `where` kind | Its own rows. The `where` above it doesn't apply to its own source. `describe` says so. |
| A kind with no fields of its own and no `where`, `source` or rules | It compiles. `advise` adds nothing. W116 doesn't fire (one parent, nothing shared). A kind can exist just to carry words, metrics or guardrails. |
| Parent and kind both bound to the same table without `where` | W116(a): "read the same rows". Give PromoSale a `where`. |
| `where` on a field the parent's file doesn't have as a column | DuckDB view creation fails. The kind lands in `skipped` with the reason, as any view does today, and `where_is` explains. |
| `where` value `promo` on an integer field | E024: "kind is a whole number in Sale; promo isn't one". |
| The parent's source is graded checked, then a `where` kind is added | The kind's source is ungraded (its own record). The parent's check is untouched. |
| An agent's proposal adds `extends` to an accepted entity | The binding fingerprint changes (it includes `extends`), so `graded_overwrites` queues it for a person. |
| `set_kind_of` on an entity whose field descriptions differ from the parent's | Kept as narrowings and listed on the review screen as "keeps its own words for revenue". |
| `make_parent` where only two children are named | Allowed, since a person asked. The rule of three governs advice, not commands. |
| `distinct:` names a pair that is no longer similar | The line stays harmless and is pruned when either side is deleted. |
| Two people mark the same pair distinct at once | The trust lock serialises the writes; the second finds it already there and says so. |
| A W116 between a parent and its own kind | Never: parent and kind are compared on own fields only, and sharing fields is the point. |
| A space at `format: 2` opened by 0.1.0 | Refused, as Part 1 says. Nothing is written by the old binary. |
| `format: 2` removed by hand while kinds remain | W118 again. Lorefile writes it back on its next save that touches a kind. |
| RDF with `rdfs:subClassOf` to a class not imported and `--no-parents` | Today's tag, with today's note. |
| Ossie `extends` naming a value type | Already handled as a value type (`kind_of_concept`). Only concepts become kinds. |
| `instances(Sale)` with a kind B kind | Only Sale's rows. `describe(Sale)` names the kind B kinds as not included. |
| `query` with `select * from sale` | Sale's view as today. Kinds have their own views: `promo_sale` (a `where` view, or its own source's view). |
| A guardrail on PromoSale referencing `promo_code`, checked for an input that takes a Sale and is a WholesaleSale | Not applied: it applies to PromoSales only. |
| `validate` with `kinds` on a key not found in the kind's rows | Like any missing row today: a note, and rules needing its fields are "unknown". |

## What changed during the build

Built on `claude/learn-file-6a954e` on top of the home plane (`f47f7bd`). All 30 decisions as recommended. Where the build differs from the text above:

1. **The DuckDB view is `PromoSale`**, named like every other entity's view, not `promo_sale`. It is `CREATE VIEW "PromoSale" AS SELECT * FROM "Sale" WHERE "kind" = 'promo'`, made after its parent's view (types are taken in ancestor-depth order).
2. **A metric on the plane belongs to the deepest `where` kind** whose every equality appears among its filter's AND-ed `field = value` terms, else to the entity whose table it reads. `channel = 'shop' and refunded = false` over `orders` belongs to ShopOrder; `total = 100 AND channel = 'shop'` to BigShopOrder, a kind of ShopOrder.
3. **Decision 11's sentence is on the metric** as `kinds_note` in `describe` (and a "Kinds:" line in its markdown): "Counts Order's rows, so it includes ShopOrders (where channel is shop) … It does not include WholesaleOrder's separate rows: never add the two."
4. **W113 on a `where` kind's binding says "perhaps because Sale's source changed"**, not "because". The fingerprint covers both the kind's `where` and the parent's source, so it can't tell which one moved.
5. **Two narrowings can't be noticed.** A typed `type: string` over a parent's number field reads as leaving the type out (string is the default), so the kind keeps the number and gets no E021. `required: false` over `required: true` reads the same way, so the field stays required. Both are in BACKLOG.
6. **Removing a parent with kinds** is refused by the save gate with one E020 per kind ("PromoSale extends Sale, which doesn't exist"), not one sentence naming them all. The review screen lists the kinds under "still uses it", as specified.
7. **The rule-of-three advice** shows in `/api/summary` (`advice`), on the review screen of a proposal that makes the third, in `match_file` when the file would be the third, and as a box on each of the entities' pages. It is not printed by `lorefile validate`, and the MCP `validate` tool (which checks actions) does not carry it.
8. **"These are different"** sits on the Home and Map card beside a W115, W116 or W117 reason, with a why box, and on the review screen as specified. The Entities page and the Logic card list no warnings today, so it is not there. A W117 shows on the entity the word names first.
9. **No "Make a common parent…" button on the page.** `make_parent` and `set_kind_of` are ops for agents and `/api/patch`; the advice box says so. The Entities page's "Make a kind of Sale…" opens the new-entity form with `extends` filled in.
10. **The "which number?" question** in `learn_file` does not offer "the same as Sale: Sale revenue" first when the parent has a metric. The rest of Part 7 is built.
11. **Take it back** leaves one thing behind: with history on, a `distinct:` said on Accept is its own commit, so Take it back keeps it (History's Undo removes it); with history off, the `format: 2` line an Accept wrote stays. Both are harmless.
12. **Imports into an existing space** (`import --from-rdf`, `--from-ossie` with `--into` an existing folder) do not rewrite its `ontology.yaml`, so a hierarchy imported there gets W118 until the next save that touches a kind, which writes `format: 2`. A new space from an import has `format: 2` from the start.
13. **The "kind of" lines are drawn simply.** On Home it is the middle stretch between the two tiles' centres, over the tiles, so it shows between neighbours; on the Map it is a straight line that may cross another node. Folding shows "+N kinds" on the parent's tile.
14. **The version is 0.2.0 in `Cargo.toml`** (and `Cargo.lock`). `npm/package.json` stays 0.1.0 in the repository because the release job sets it from the crate's version at publish time. There was no CHANGELOG, so `CHANGELOG.md` is new, with Part 1's release note.
